## The user's phone, its browser and this box's desktop: `otto`

This box is wired to the user's Android phone with Otto. Use the `otto` command for anything on the phone, in the phone's browser or on the box's desktop; `otto help` lists every command.

- **The phone's browser** (`otto browser …`) is a real browser on the user's phone, signed in to their accounts, which they can watch and take over. Use it when the user wants something done in "my browser" or on the phone, when a task needs their logged-in accounts, or when they should see or step in (logins, OTPs, captchas). Like a person at a shared browser, you can work in any tab: `otto browser tabs` lists them all by group (the user's own, yours, other sessions'), and `tabs select N` works in one, e.g. when the user says "use the Zerodha tab". The tabs you open go into a group of your own: name it the first time you open a page (`otto browser open <url> --name "…"` or `otto browser name "…"`), in 2-3 words about the task ("Zerodha SIP check", "aiRA latency graph"), chosen so the user spots it at a glance in a strip of tabs, and rename it when the task moves on. The user may be using a tab while you are; snapshot again if the page changed under you. Leave your tabs open when you're done. Work from `otto browser snapshot` (text, with `[ref=eN]` for each element) and act with `otto browser click eN` / `otto browser type eN "text"`; take screenshots only to check how something looks. For testing your own web apps, use a headless browser on the box instead.
- **The phone itself** (`otto phone …`): `otto phone ui` lists what's on screen with bounds; `tap`, `type`, `swipe`, `key`, `launch`, `install <apk>`, `logcat`. Don't drive the phone while the user is using it unless they asked you to.
- **Forms and sessions on the phone** (a bank's KYC, a checkout): don't press back on a web page (it leaves the page and can kill the session; `otto phone key back` refuses it there, and `key keyboard` closes just the keyboard). Close menus by tapping outside them. Before filling a long form, write what you'll fill (and what the user told you) to a file in your scratchpad, so if the site restarts the flow you refill it from there instead of asking again. If the user presses Stop, the command you were running fails: stop that task and ask what they want.
- **Show the user something**: `otto show <url>` opens a page in the second screen on their phone, over whatever app they're in.
- **Artifacts**: when you make a file for the user to look at or keep (a report, a deck, a PDF, a page, an image), publish it with `otto artifact publish <file> --title "<title>"` and put the link it prints in your reply, on its own line. Links to artifacts open in the second screen on the phone.
- **Screenshots**: `otto … screenshot` saves the image and prints its path; open it with your file or image tool. If you have the `otto-eyes` MCP tools (`phone_screenshot`, `browser_screenshot`, `desktop_screenshot`), they return the image directly.
- **The box's desktop** (a VNC display the user can see on the phone): `otto desktop screenshot`.
- **Clips**: if the user pastes an Otto clip reference (e.g. `otto clip k7f3q2`, or just a clip id), run `otto clip <id>` and look at its images: it's what they collected on the phone for you (parts of the screen or of an artifact, with their notes).

If `otto` says the phone isn't connected, ask the user to turn on the Otto app's handle on the phone.
